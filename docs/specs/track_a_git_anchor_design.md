# Track A Git実用アンカー設計メモ

作成日: 2026-06-09

## 1. 目的

Track A を「近接論文アンカー」だけでなく、研究テーマに直接つながる **実装・制約・失敗パターンのアンカー** として再定義する。
Track B が遠い構造類推を担うのに対し、Track A は「今すぐ触れる現実」を提示する層とする。

本メモは設計案であり、実装・`plan.md` 反映前の一次整理とする。

## 2. 再定義

### 2.1 旧Track A

- テーマに近い論文を少数添えて、Track B の遠さを測るための文脈アンカーにする

### 2.2 新Track A

- テーマに直接関連する OSS / GitHub repository を少数添えて、Track B の遠さを測るための **実務アンカー** にする
- 目的は「論文として近い」ことではなく、「テーマを現実に動かしたときに何が制約になるか」を見せること
- 出力では以下を優先して示す
  - 実装の入口
  - 依存技術や運用制約
  - README / issue / commit に現れる失敗パターン
  - 再現性や保守性の匂い

### 2.3 役割分担

- Track A: 近接・実務・足場
- Track B: 遠方・構造類推・視座拡張

両者は競合させず、ユーザーに「今すぐ試せる現実」と「遠いが効く発想」を並置して渡す。

## 3. 対象リポジトリの収集条件

### 3.1 ハード条件

- 公開リポジトリであること
- README が存在し、テーマとの関連が本文で判読できること
- ライセンスが明示されていること
- デフォルトブランチ上に最低限の活動履歴があること

### 3.2 検索クエリの原則

- テーマ核心語を主軸にする
- 研究タスク語を混ぜる
  - 例: `benchmark`, `dataset`, `training`, `simulation`, `inference`, `evaluation`, `pipeline`
- 実装語を混ぜる
  - 例: `github`, `repository`, `implementation`, `code`, `toolkit`, `framework`
- 除外語はテーマ入力の `keywords.exclude` を尊重する
- Track B と違い、別ドメイン化は狙わない

### 3.3 検索の意図

- Track A は「テーマそのものを誰がどう実装しているか」を探す
- 論文付随コードだけに寄せず、周辺ツール・評価基盤・再現実験コードも許容する
- ただし単なるawesome listやリンク集は原則除外する

## 4. 選定基準

Track A 候補は、テーマ近接性だけでなく「実用アンカーとしての価値」で評価する。

### 4.1 優先するもの

- README が用途・入力・出力・前提条件を明記している
- セットアップや実行手順が具体的
- issue / discussion に詰まりどころや制約が出ている
- commit 履歴から継続利用の痕跡がある
- 論文やデータセットへの参照があり、研究文脈との接続が分かる

### 4.2 除外または強い減点

- README がほぼ空
- ライセンス不明
- 最終更新が古く、かつ issue も閉塞している
- 生成物置き場に近く、コードや再現手順がほぼ無い
- テーマ核心語は含むが用途がズレている
- フォークで独自価値が薄い

## 5. 信頼性評価軸

Git 由来情報は論文以上にノイズが大きいため、単一指標でなく複数指標で評価する。

### 5.1 Repository Reliability Score（暫定）

合計 100 点の加点方式を想定する。実装時は閾値よりも、説明可能な内訳表示を優先する。

| 軸 | 配点 | 観点 |
|---|---:|---|
| Theme Fit | 30 | README / topics / 主要ファイルから見てテーマに直接関係するか |
| Activity | 15 | 最終更新、直近コミット頻度、放置状態の有無 |
| Adoption | 15 | stars / forks / watchers の極端な弱さがないか |
| License | 10 | 明示ライセンスがあるか、再利用可能か |
| README Completeness | 15 | 目的、セットアップ、使用例、制約が書かれているか |
| Issue Signal | 10 | issue / discussion に再現困難点や障害が現れているか |
| Research Linkage | 5 | 論文・データセット・ベンチマークとの参照関係があるか |

### 5.2 解釈ルール

- stars は人気の代理であり、品質の保証ではない
- last commit は保守の匂いとして使うが、新規性や完成度を単独では判定しない
- issue quality は量ではなく「詰まりどころが読めるか」を見る
- README completeness は Track A の価値に直結するため重めに扱う

## 6. 出力フォーマット案

Track A は論文と同じ4部構成へ無理に揃えず、Gitリポジトリに適した短い実務フォーマットにする。

### 6.1 1件あたりの出力項目

1. リポジトリ名 + URL
2. テーマとの関係ラベル
   - 例: `【実装アンカー】`, `【評価基盤】`, `【再現コード】`, `【制約露出】`
3. 何が直接使えるか
4. どの制約 / 失敗パターンが見えるか
5. 信頼性メモ
   - 例: `stars`, `last commit`, `license`, `README`, `issues`

### 6.2 表示例

```text
- repo: example/project
  【実装アンカー】
  何が使えるか: テーマの中核タスクをそのまま実行できる最小実装。
  制約/失敗パターン: GPU 前提・依存が重く、issue でも環境差分の詰まりが多い。
  信頼性メモ: MIT / stars 420 / last commit 3 months ago / README 充実 / issues に再現報告あり
```

## 7. Track B との表示区分

### 7.1 混同してはいけない点

- Track A は「近い現実」
- Track B は「遠い発想」

Track A に遠さや意外性を求めない。Track B に即実装性を求めない。

### 7.2 UI / Markdown レベルでの区分案

- Track B を本文の主役として先に出す
- Track A は末尾の補助セクションに置く
- Track A 見出しは `Practical Anchors` のように、論文群と異なる名前を使う
- Track A のラベル語彙は「実装」「評価」「制約」に限定し、「接続点」「類推」など Track B 語彙を使わない

## 8. 実装に落とすときの最小単位

1. GitHub 検索クエリ生成
2. リポジトリ最小メタデータ取得
   - name, url, description, stars, forks, updated_at, license, topics
3. README 要約
4. issue / discussion の軽い観測
5. Repository Reliability Score 算出
6. Track A Markdown レンダリング

Phase 1 では「検索 + README/メタデータ要約」まででもよい。issue 深掘りは Phase 2 候補。

## 9. 非目標

- GitHub 全文検索基盤の構築
- コード品質の厳密静的解析
- 自動セットアップや実行検証
- Track A と Track B の統一スコアリング

## 10. 結論

Track A の Git 版は、近接論文の代用品ではなく、**テーマを現実に引き戻すための実用アンカー層**として扱うのが妥当。
contra の中核は引き続き Track B に置きつつ、Track A では「直接使える実装」「露出した制約」「失敗の匂い」を見せる。
